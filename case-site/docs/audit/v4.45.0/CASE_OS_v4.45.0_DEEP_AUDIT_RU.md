# CASE OS v4.45.0 - глубокий аудит и перепрошивка платформы

Исходная рабочая версия: `CASE_OS_v4.44.0_FULL.zip`

## 1. Итог

Платформа сохранена как единая рабочая система без удаления исходных файлов, модулей, справочников, планировок, геоданных, документов и бизнес-данных. Обновление выполнено поверх копии v4.44.0 с минимальным вмешательством в проверенную бизнес-логику.

Версия повышена до **v4.45.0**, поскольку обновление включает средний функциональный релиз:

- единый UX-слой для всей платформы;
- адаптивную оболочку для широких, средних и малых экранов;
- усиление ролевой логики на клиенте и сервере;
- новый аналитический модуль «Отчёт владельцу»;
- отчёты в виде текста, таблиц и планировки;
- неизменяемые снимки отчётов;
- улучшения доступности и клавиатурной работы;
- унификацию короткого тире в отображаемом интерфейсе;
- устранение повторяющихся системных уведомлений.

## 3. Основные проблемы v4.44.0

### 3.1. Перегруженность на средних экранах

На ширине около 1024 px закреплённая боковая панель занимала примерно 264 px. Для LCR и аналитики оставалось около 745 px, из-за чего таблицы и панели управления выглядели тесно.

### 3.2. Непоследовательная ролевaя логика

Были обнаружены расхождения между описанием роли, рабочей областью и прямым открытием маршрута:

- внешний агент AGX мог попытаться открыть корпоративный реестр прямым маршрутом;
- младший администратор данных BRJ получал в стандартной рабочей области реестр и проекты, хотя описание роли прямо запрещало этот доступ;
- архитектор BSH должен был видеть реестр только для просмотра, но реестр отсутствовал в его стандартной рабочей области;
- универсальное право `edit` могло быть ошибочно истолковано как право архитектора или BRJ изменять LCR.

### 3.3. Недостаточная доступность legacy-экранов

Статический аудит обнаружил большое количество старых элементов без явных подписей, несемантические `onclick`-элементы, отсутствующие alt-тексты и локальные правила, убирающие focus outline.

### 3.4. Длинный и тяжёлый главный экран

Для руководителей главный экран показывал сразу всю операционную детализацию. Ключевые исключения и показатели терялись в длинной странице.

### 3.5. Отсутствие полноценного отчёта владельцу

В системе не было единого отчёта, который из одного снимка данных показывал бы:

- GLA и заполненность;
- площадь по статусам;
- бренды по статусам;
- подписанные сделки;
- активные переговоры;
- отказы и причины;
- планировку с цветовой индикацией;
- динамику относительно предыдущей версии отчёта.

### 3.6. Повторяющиеся уведомления

Если браузер блокировал localStorage или был переполнен, одинаковое сообщение о невозможности сохранения могло появляться много раз и закрывать рабочую область.

### 3.7. Разные типографические тире

В интерфейсе одновременно использовались длинные тире, средние тире и короткие дефисы. Это нарушало визуальную унифицированность.

## 4. Что изменено

### 4.1. Единый UX-слой

Добавлен файл `os/v4450-ux-system.js`.

Он обеспечивает:

- единые focus-состояния;
- автоматические aria-label для legacy-контролов;
- alt-тексты для изображений без alt;
- клавиатурную активацию старых кликабельных элементов;
- семантические роли для прокручиваемых таблиц;
- единый адаптивный каркас;
- короткое тире во всём отображаемом интерфейсе без изменения сохранённых данных;
- ограничение повторяющихся toast-сообщений;
- максимум три одновременных уведомления;
- поддержку `prefers-reduced-motion`;
- минимальную высоту основных мобильных контролов 44 px.

### 4.2. Адаптивная оболочка

Новая логика:

- от 1200 px - полная закреплённая навигация шириной 224 px;
- от 821 до 1199 px - компактная боковая панель шириной 64 px с раскрытием при наведении;
- до 820 px - мобильная выдвижная навигация;
- поиск переносится на отдельную строку только при необходимости;
- нижеприоритетные действия остаются в существующих меню «Ещё»;
- ширина главной рабочей области увеличена без изменения бизнес-контента.

### 4.3. Главный экран для разных типов пользователей

Добавлены режимы:

- **Сводка** - для генерального директора, финансового директора и администратора;
- **Подробно** - для операционной работы.

Выбор сохраняется отдельно для каждого пользователя.

### 4.4. Ролевые ограничения

Роль AGX:

- только рабочий стол, задачи, канбан, отправка новых брендов и разрешённые заявки;
- нет LCR, внутренних проектов, контактов, финансов и корпоративных баз;
- прямой маршрут в закрытый раздел показывает безопасный экран отказа без загрузки содержимого.

Роль BRJ:

- база брендов, геоаналитика, рыночные данные и качество данных;
- нет LCR, реестра аренды и карточек проектов;
- старые сохранённые пользовательские рабочие области автоматически очищаются от запрещённых модулей.

Роль BSH:

- планировки и архитектурные инструменты;
- реестр LCR только для просмотра;
- кнопки изменения скрыты;
- API `unit_patch.php` и `units_batch.php` отклоняют изменения LCR.

Проверки выполняются и на клиенте, и на сервере.

### 4.5. Отчёт владельцу

Добавлен файл `os/v4450-owner-report.js`.

Отчёт доступен из проекта, LCR, планировок и главного экрана для разрешённых ролей.

Поддерживаются три представления:

1. Комбинированный отчёт.
2. Таблица и текст.
3. Планировка.

Разделы отчёта:

- сводка;
- площадь по статусам;
- бренды;
- отказы;
- планировка;
- проверка данных;
- сохранённые версии.

Ключевая логика:

- каждый юнит учитывается в площади только один раз;
- несколько брендов по одному юниту не увеличивают GLA;
- статус площади определяется текущим статусом юнита;
- таблицы, текст и планировка строятся из одного снимка;
- при наличии связанного SVG используется фактическая планировка;
- при отсутствии SVG формируется понятная схематическая планировка;
- версия отчёта сохраняется отдельно и не меняется вслед за LCR.

Экспорт:

- печать и PDF;
- Excel/CSV;
- PPTX;
- сохранённый снимок в истории проекта.

### 4.6. Безопасность отчёта владельцу

Сохранённая версия принудительно переводится в профиль владельца и очищается от:

- внутренних ставок;
- арендных расчётов;
- брокеров;
- внутренних комментариев;
- контактов;
- комиссий.

На сервере история `OWNER_REPORTS` сделана append-only:

- старый снимок нельзя удалить обычным сохранением общего состояния;
- старый снимок нельзя перезаписать по существующему ID;
- новый снимок повторно очищается на сервере;
- автор и время создания устанавливаются сервером.

## 8. Что сознательно не переписывалось

Чтобы не повредить рабочую систему, не выполнялась массовая замена всех legacy-компонентов и таблиц. Проверенный CASE Data Grid, LCR, SCR, геоаналитика, финансовые модели, документы и рабочие данные сохранены.

Статический аудитор по-прежнему видит технический долг в исходном legacy-коде:

- очень мелкие служебные подписи;
- фиксированные ширины некоторых специализированных студий;
- emoji-иконки в старых модулях;
- старые несемантические обработчики.

Безопасные проблемы исправляются единым runtime-слоем. Полное физическое переписывание этих компонентов рекомендуется делать постепенно по модулю, а не одной большой заменой.

## 9. Ограничения текущей проверки

В среде проверки управляемая политика Chromium блокировала переходы на `localhost` и `file://`. Поэтому браузерные проверки выполнялись на самодостаточном production-bundle, загруженном через Chrome DevTools Protocol.

Фактически проверены интерфейс, JavaScript-логика, маршруты, роли, отчёты и адаптивность. На staging-сервере дополнительно необходимо проверить:

- реальный PHP/MySQL вход;
- параллельное сохранение несколькими сотрудниками;
- внешние карты и CDN;
- отправку файлов PPTX/CSV браузером;
- печать в PDF;
- Service Worker после обновления кэша;
- восстановление из резервной копии.
