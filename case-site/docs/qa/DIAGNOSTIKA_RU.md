# Глубокая проверка платформы: два скрипта

Проверка состоит из двух частей, потому что причины сбоев бывают на двух разных сторонах:

| Что проверяем | Чем | Где запускать |
|---|---|---|
| Сервер: файлы, база, права сотрудников, история пропаж | `server_check.php` | терминал хостинга |
| Браузер сотрудника: что реально загрузилось, кэш, связь с сервером | `browser_check.js` | консоль браузера (F12) |

Оба скрипта **только читают**. Они ничего не меняют, не удаляют и не пишут в базу.
Пароли, ключи и содержимое `config.php` не выводятся — печатается только «задан / не задан».
Вывод можно пересылать целиком.

---

## 1. Серверная проверка (терминал DirectAdmin)

**Шаг 1.** Возьмите файл `docs/qa/tools/server_check.php` из репозитория и залейте его
через файловый менеджер DirectAdmin в папку `os` вашего сайта — туда же, где лежит `index.html`.

**Шаг 2.** Откройте в DirectAdmin: **Дополнительно → Терминал** (или SSH).

**Шаг 3.** Выполните две команды:

```bash
cd ~/domains/caseadvisory.uz/public_html/os
php server_check.php
```

Если путь другой, найдите его так:

```bash
find ~ -name index.html -path "*/os/*" 2>/dev/null
```

**Шаг 4.** Скопируйте весь вывод и пришлите мне.

Чтобы сохранить в файл и скачать через файловый менеджер:

```bash
php server_check.php > check.txt
```

**Шаг 5. Обязательно.** После проверки удалите скрипт с сервера:

```bash
rm server_check.php
```

Запуск через браузер скрипт блокирует сам (отдаёт 403 и ничего не показывает),
но лишний файл на боевом сервере держать незачем.

### Что покажет серверная проверка

1. **Файлы и версии** — сверка каждого модуля: что ждёт `index.html` против того, что реально
   лежит на диске, плюс контрольные суммы. Ловит ту самую «залил не всё» ситуацию.
2. **Окружение PHP** — расширения и лимиты. Отдельно предупреждает, если `post_max_size`
   меньше 16 МБ: при большой базе сохранение будет обрываться на полпути.
3. **База данных** — подключение, список таблиц и число строк.
4. **Сотрудники и права** — таблица «кто может сохранять». Если у активного сотрудника
   `правка = НЕТ`, он физически не может ничего сохранить, и для него это выглядит
   ровно как «ввёл данные, обновил страницу, всё пропало».
5. **Данные платформы** — сколько объектов, помещений, брендов, вариантов подбора и геозаписей
   реально лежит на сервере.
6. **История правок в помещениях** — все записи со словом «очищено»: когда и под чьей учётной
   записью список вариантов обнулялся.
7. **История геоданных** — по снимкам видно объём на каждый момент; строка с пометкой
   **«РЕЗКОЕ ПАДЕНИЕ»** показывает, когда и кто обвалил базу. К любому снимку можно вернуться:
   Геоаналитика → «История / восстановление».
8. **Журнал действий** — отказы в сохранении. Запись `state_key_denied` означает, что сотрудник
   пытался сохранить раздел, закрытый для его роли.
9. **Личные настройки таблиц** и **10. последние ошибки PHP**.

## 2. Проверка со стороны браузера

Серверный скрипт видит сервер, но не видит, что загрузилось у конкретного сотрудника:
старый кэш, недокачанный модуль, отсутствующее право. Это проверяет второй скрипт.

**Шаг 1.** Сотрудник, у которого пропадают данные, открывает сайт и **входит под своей учётной записью**.

**Шаг 2.** Нажимает `F12` → вкладка **Console** (Консоль).

**Шаг 3.** Открывает `docs/qa/tools/browser_check.js`, копирует содержимое целиком,
вставляет в консоль и нажимает Enter.

**Шаг 4.** Через пару секунд появится отчёт — он сам копируется в буфер обмена.
Пришлите его мне.

Полезно запускать проверку **на экране Реестра, прокрутив страницу к таблице**: тогда
скрипт дополнительно проверит, что шапка таблицы действительно отрисована.

### Что покажет браузерная проверка

1. **Версия и модули** — что реально загрузилось у сотрудника. Расхождение здесь при
   зелёном сервере означает старый кэш: помогает `Ctrl+Shift+R`.
2. **Кэш и Service Worker** — остались ли кэши прошлых версий.
3. **Пользователь и права** — роль и её права, включая `edit` и `geoEdit`.
4. **Данные в браузере** — сколько объектов, помещений, вариантов подбора и геозаписей загружено.
5. **Связь с сервером** — живой запрос к `api/state.php`: код ответа, время, ревизия.
   Отдельно сверяет число помещений в браузере и на сервере — расхождение означает,
   что часть данных не долетела. Ответ 401/403 означает, что сессия не признаётся
   и сохранение работать не будет.
6. **Таблицы на экране** — проверка, что шапка реально отрисована, а не просто числится
   в разметке.
7. **Ошибки** — при первом запуске включается перехват. Поработайте 2–3 минуты и запустите
   скрипт ещё раз: во втором отчёте будут все ошибки, которые возникли за это время.

## Как читать результат

Строки помечены:

- `OK` — проверка пройдена;
- `!!` — проблема, на неё нужно смотреть.

Быстрое сопоставление жалоб и разделов:

| Жалоба сотрудника | Куда смотреть |
|---|---|
| «ввёл данные, обновил — пропали» | сервер §4 (право `правка`), сервер §8 (`state_key_denied`), браузер §5 (код ответа) |
| «пропали варианты подбора» | сервер §6 (записи «очищено») |
| «пропали геоданные» | сервер §7 (пометка «РЕЗКОЕ ПАДЕНИЕ») |
| «интерфейс старый / кнопки не те» | браузер §1 и §2 (кэш), сервер §1 (полнота заливки) |
| «таблица разъезжается» | браузер §6 |
| «сохранение долго идёт и обрывается» | сервер §2 (`post_max_size`) |
