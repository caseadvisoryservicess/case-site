# CASE OS — как обновлять платформу без потери данных

## Главный принцип
Данные и код разделены:
- **Данные** — в MySQL на вашем хостинге. Обновление кода их **не трогает**.
- **Код** — `os/index.html` и `os/api/*.php`. Обновить = заменить файлы.

Поэтому новую версию можно ставить поверх рабочей — данные остаются.

> Важно: `os/api/config.php` (данные подключения к БД) — **не включайте**
> в загрузку обновлений и не перезаписывайте. Он создаётся один раз.

---

## Сценарий A. Обычное обновление (без изменения структуры БД)
Большинство обновлений (правки интерфейса, логики, документов).

1. **Бэкап БД** (на всякий случай): cPanel → phpMyAdmin → выбрать БД →
   **Export** → Go. Сохранить файл.
2. Заменить на хостинге `os/index.html` (и при изменениях — `os/api/*.php`,
   кроме `config.php`).
3. Если менялся `os/sw.js` — поднять в нём версию кэша
   (`const CACHE = 'case-os-vN'` → `vN+1`), чтобы у пользователей подтянулась
   новая версия, а не старая из кэша.

Данные в БД не меняются. Готово.

---

## Сценарий B. Обновление со структурой БД (новые поля/таблицы)
Когда новая версия требует изменений в базе.

1. **Бэкап БД** (обязательно).
2. Положить файл миграции в `os/sql/migrations/`, имя с датой, напр.
   `2026_07_15_add_field.sql`. Внутри — только **аддитивные**, идемпотентные
   изменения:
   ```sql
   ALTER TABLE units ADD COLUMN IF NOT EXISTS new_field VARCHAR(120) NULL;
   CREATE TABLE IF NOT EXISTS new_table (...);
   ```
3. Залить новые файлы (включая миграцию и обновлённый код).
4. Войти администратором и открыть `…/os/api/migrate.php` (POST; можно из
   платформы кнопкой «Применить миграции»). Применятся **только новые**
   файлы; уже применённые пропускаются. Данные сохраняются.

Что **нельзя** в обычных обновлениях: `DROP TABLE`, `DROP COLUMN`,
`TRUNCATE`, повторный запуск `schema_mysql.sql` на боевой БД
(он только для чистой установки).

---

## Бэкапы
- Перед каждым обновлением — экспорт БД (phpMyAdmin → Export).
- Дополнительно: cPanel → **Backup** (полный бэкап аккаунта) по расписанию.
- Файлы кода тоже стоит хранить (этот репозиторий — история версий).

---

## Рекомендуемая практика (по желанию)
Сделать **тестовую копию** для проверки перед боевым обновлением:
- папка `os-test/` + отдельная тестовая БД (копия дампа);
- проверить новую версию там, затем заменить боевую.

Так обновления идут без риска для рабочих данных.
